# 6. Deployment

Three ways to run this, in increasing order of permanence. All three run
the same code; only the database and the process manager change.

| Way | Postgres | Use it when |
|---|---|---|
| **Local, no Docker** | A free Neon project | Docker is not installed. This is how the project was built. |
| **`docker compose up`** | A container | Docker is installed and you want one command. |
| **Render + Vercel** | Render's managed Postgres | You want a URL to send someone. |

---

## 1. Local, without Docker

This machine had no Docker, so this is the path that is actually
exercised. The schema depends on Postgres-specific features — enum types,
`JSONB`, partial indexes, constraint triggers, `CITEXT` — so SQLite is not
a fallback, and a hosted Postgres is the shortest way to a real one.

1. Create a free project at [neon.tech](https://neon.tech). No card.
2. Copy the connection string into `.env`:

```bash
DATABASE_URL=postgresql://user:pass@ep-xxx.ap-southeast-1.aws.neon.tech/tallyproof?sslmode=require
```

The driver suffix is optional. `config.py` normalises `postgres://` and
`postgresql://` to `postgresql+asyncpg://`, because every managed
provider emits one of those and a driverless URL resolves to psycopg2 —
synchronous, and rejected by `create_async_engine` on the first request.
That failure only shows up on the platform, never locally, which is why
it is handled in code rather than in a README instruction someone skips.

3. Apply the schema and run:

```bash
make migrate
```

```bash
make api
```

```bash
make web
```

`make migrate` runs Alembic revision `0001`, which applies `db/schema.sql`
verbatim rather than an autogenerated equivalent. Roughly a third of that
file is invisible to SQLAlchemy's autogenerate — the append-only trigger
on `decision_audit_events`, the split-allocation constraint trigger, the
partial unique index that stops one transaction being counted in two
groups — and a migration without those is not the same schema.

### Until a database exists

The API runs anyway — `PERSISTENCE` defaults to `memory`, and `config.py` refuses that value when `ENVIRONMENT=production`. Persistence sits behind a protocol with an in-memory
implementation, so every endpoint works, the engine runs, and the
frontend is live. `/healthz` returns 200; `/readyz` returns 503 naming the
database as the reason. That is the correct behaviour rather than a
failure to boot — a process that refuses to start without its database
cannot serve the health check that tells you the database is what is
down.

The in-memory store has no durability, no concurrent writers, and none of
the schema's constraints or triggers. It is right for development and
wrong for a deployment.

## 2. `docker compose up --build`

Postgres, the API and the frontend, wired together. The API container
runs `alembic upgrade head` before starting, and waits on Postgres's
health check first — `pg_isready` returns true while the server is still
running its first-boot `initdb`, which is long enough for a migration to
connect and fail.

Both images build from the repository root, not from their own
directories, because the API imports the three framework-free packages
under `packages/`. A `backend/`-only build context produces an image that
fails at import rather than at build, which is a worse place to find out.

```bash
docker compose up --build
```

API on `:8000`, frontend on `:3000`, Postgres on `:5432`. The demo
accounts are seeded (`SEED_DEMO_USERS=true`), password
`tallyproof-demo-2026`.

## 3. Render (API + Postgres) and Vercel (web)

`render.yaml` is the whole API deployment. Point Render at the repository
and it reads it:

- **Postgres 16**, private network only (`ipAllowList: []`).
- **The API** from `backend/Dockerfile`, with `preDeployCommand` running
  migrations *before* the new instance takes traffic. Running them from
  application startup instead would race every replica against every
  other one.
- `JWT_SECRET` via `generateValue: true` — 256 bits, generated once by
  the platform, never in git.
- `SEED_DEMO_USERS: "false"`. `config.py` refuses to create those
  accounts when `ENVIRONMENT=production` regardless, but the guard should
  not be the only thing between a password published in a README and a
  live system.

Two values are `sync: false`, meaning Render prompts once and stores
them:

| Variable | Value |
|---|---|
| `FRONTEND_ORIGIN` | The exact Vercel URL, e.g. `https://tallyproof.vercel.app` |
| `AI_API_KEY` | Only if you set `AI_ENABLED=true` |

`FRONTEND_ORIGIN` must be exact. CORS uses it with `allow_credentials`,
and browsers silently ignore a wildcard origin once credentials are
involved — which reads as "auth is broken in production" on the day you
can least afford to debug it.

### The frontend on Vercel

Import the repository, set the root directory to `frontend/`, and set one
environment variable:

```
API_URL=https://ledgergraph-api.onrender.com
```

`API_URL`, not `NEXT_PUBLIC_API_URL`. The browser never calls the API
directly — every request goes through a Server Component, a Server
Action, or the export route handler, all of which attach the session
token server-side. A `NEXT_PUBLIC_` variable would ship the API's address
to the client for no purpose.

### Ordering

`FRONTEND_ORIGIN` needs the Vercel URL and `API_URL` needs the Render
URL, so:

1. Deploy the API. Note its URL.
2. Deploy the frontend with `API_URL` set. Note its URL.
3. Set `FRONTEND_ORIGIN` on Render to the Vercel URL. Redeploy the API.

Step 3 is not optional. Until it is done the frontend renders and every
API call fails CORS.

## Cookies across two origins

Locally, the frontend and API are both on `localhost`, so
`SameSite=Lax` works and the cross-site case never appears in
development. Deployed, they are on different registrable domains, and the
refresh cookie needs `SameSite=None; Secure` or the browser drops it
silently — no error, no console warning, just a session that will not
persist.

`auth.py` derives this from `settings.is_local` rather than hardcoding
it, so the same code is correct in both places:

```python
cross_site = not settings.is_local
"secure": cross_site,
"samesite": "none" if cross_site else "lax",
```

The Next.js session cookies are a separate matter: they are same-origin
with the app, `httpOnly`, and `secure` in production.

## What is deployed, and what is not

| Piece | State |
|---|---|
| API image, non-root, health-checked | Written |
| Frontend image, standalone output | Written |
| `render.yaml`, secrets as `sync: false` / `generateValue` | Written |
| `docker-compose.yml` with a real health gate | Written |
| Driver normalisation for managed Postgres | **Written and tested** |
| Postgres `Repository` implementation | Written; **never executed against a server** |
| `db/schema.sql` executed against a real Postgres | **Never** — no database has been reachable from this machine |

That last row is the honest one. The schema is parsed with
`libpg_query` — PostgreSQL's own parser, lifted out of the server — and
cross-checked for foreign keys, enum types, index columns and trigger
functions that resolve (`tests/unit/test_schema_sql.py`, verified by
mutation: six injected defects, six caught). That is not the same as
having applied it. `make migrate` remains the first real test, and it
needs a `DATABASE_URL`.
